# Data formats

Every file the app reads or writes is specified here. Column names are the Room column names in
`core/data/src/main/kotlin/org/fieldcapture/data/Entities.kt`, so the SQLite export and the CSVs agree
by construction. All timestamps are ISO 8601 UTC with milliseconds (`2026-06-14T15:04:05.123Z`);
`*_local` columns, where present, carry the device's local time for humans. Coordinates are WGS 84
decimal degrees with seven decimals. CSVs are UTF-8, comma-delimited, CRLF, RFC 4180 quoting, header row
always present. Parsers reject a file that fails the contract and report row-numbered issues; nothing is
silently coerced.

## Field layout import (Field Book–compatible)

Accepted: `.csv`, `.xlsx` (converted to rows by `:core:data`; `.xls` is not supported in M1). Field Book
requires a unique identifier column, a primary and a secondary ordering column, and allows any further
columns; header names must not contain `/ ? * | "` [web: https://docs.fieldbook.phenoapps.org/en/latest/fields.html,
https://raw.githubusercontent.com/PhenoApps/Field-Book/main/docs/fields.md]. Entry coordinates use a
`geo_coordinates` column documented as `Lat;Long` [web:
https://raw.githubusercontent.com/PhenoApps/Field-Book/main/docs/geonav.md]; the bundled `rtk_sample.csv`
contains `-96.3431604;36.6677618`, which is lon;lat [web:
https://raw.githubusercontent.com/PhenoApps/Field-Book/main/app/src/main/assets/field_import/rtk_sample.csv].
The importer accepts both orders by range check and warns when it had to swap (see
`FieldBookImport.parseGeoCoordinates`).

| Column | Required | Meaning |
|---|---|---|
| unique identifier (user-selected; auto-detected as `plot_id`, `unique_id`, `plotid`, `id`, else first column) | yes | `plot_id` everywhere in this app; must be unique across the file |
| primary id (auto-detected as `row`, `range`, `primary_id`, `block`) | yes | first ordering column |
| secondary id (auto-detected as `plot`, `column`, `col`, `secondary_id`) | yes | second ordering column |
| `geo_coordinates` | no | `lat;lon` (or `lon;lat`, detected); becomes the plot centroid with `coord_source = IMPORT` |
| any other | no | stored verbatim in `attributes_json` and round-tripped to exports |

Planting order defaults to file row order, which is also what Field Book's "entry numbers" express
[web: fields.md]; the field detail screen can re-sort by primary/secondary before planting.

Example (first rows of Field Book's sample):

```
plot_id,row,column,plot,tray_row,tray_id,seed_id,seed_name,pedigree,geo_coordinates
13RPN00001,1,1,1,1,13RPN_TRAY001,12GHT00001B,Kharkof,Kharkof,-96.3431604;36.6677618
13RPN00002,1,2,2,3,13RPN_TRAY001,12GHT00002B,Roughrider,Roughrider,
```

## Grid layout (no import file)

Inputs: origin (lat, lon), range bearing (degrees from north), rows, ranges, row spacing (m), range
length (m), alley (m), rows per plot. Output: plots `R{range}P{across}` with `row`/`range` attributes,
centroid and rectangle polygon, serpentine or linear planting order. Generated by `GridLayout` and stored
with `coord_source = GRID`. Planter mode later overwrites centroids with measured fixes
(`coord_source = PLANTER`) and keeps the grid polygon.

## Export bundle

An export is a folder `field_export/<trial>_<field>_<yyyyMMddTHHmmssZ>/` (or a `.zip` of it) written to a
location the user chooses. Contents:

| File | Always | Contract |
|---|---|---|
| `manifest.json` | yes | app version, schema version, device, export time, list of files with SHA-256, trial/field ids, coordinate datum, note on sensitivity |
| `plots.csv` | yes | dimension table (below) |
| `plots.geojson` | yes | FeatureCollection; Polygon where known else Point; properties = `plots.csv` columns |
| `planter_events.csv` | if any | fact table (below) |
| `annotations.csv` | if any | fact table (below) |
| `observations.csv` | if any | long format, one row per trait value |
| `media.csv` | if any | one row per photo/video/audio file with relative path |
| `points.geojson` | if any | Point features for planter events, annotations and media, `kind` property distinguishes them |
| `tracks/<session_id>.gpx` | if any | GPX 1.1, one `trk` per session, `fc:accuracy_m`/`fc:speed_mps`/`fc:provider` extensions |
| `fieldcapture.sqlite` | optional | byte copy of the Room database after a WAL checkpoint; schema version in `manifest.json` |
| `fieldbook_table.csv`, `fieldbook_database.csv` | optional | Field Book Table and Database layouts (below) |
| `sample_manifest.csv` | optional | plate layout (below) |
| `weather_daily.csv`, `soil.csv`, `harvest.csv`, `crosses.csv` | optional | integration tables |
| `media/<trial>/<field>/<plot_id>/<note_type>/…` | optional | copied media files plus sidecars |

## observations.csv

`observation_id, plot_id, session_id, annotation_id, trait, value, unit, timestamp, person, source, lat, lon`.
`source` is `VOICE` (parsed from a transcript such as "lodging three"), `MANUAL`, or `IMPORT`. Trait
names are free text in M2; a trait dictionary with units is an M4 item.

## media.csv and the media folder

Folder: `media/<trial>/<field>/<plot_id>/<note_type>/<yyyyMMddTHHmmssZ>_<seq>.<ext>`. Segments are
sanitized to `[A-Za-z0-9._-]` by `MediaPath.segment`; the sanitized values are also what appear in
`media.csv` so joins work on the file system alone. `note_type` is the trait or note category the user
picked (`photo`, `lodging`, `disease`, `plant_stand`, …).

| Column | Type | Notes |
|---|---|---|
| `media_id` | text | UUID |
| `type` | text | `PHOTO`, `VIDEO`, `AUDIO` |
| `plot_id`, `session_id` | text | |
| `note_type` | text | |
| `path` | text | relative to the export root |
| `sidecar_path` | text | same stem, `.json` |
| `timestamp` | timestamp | |
| `lat`, `lon`, `accuracy_m`, `bearing_deg` | real | |
| `sha256` | text | |
| `bytes` | int | |

EXIF on photos (androidx ExifInterface): `GPSLatitude/GPSLongitude` via `setLatLong`,
`GPSTimeStamp`/`GPSDateStamp`, `DateTimeOriginal`, `ImageDescription` = `plot_id`, `UserComment` = a
compact JSON with `trial`, `field`, `plot_id`, `note_type`, `session_id` [web:
https://developer.android.com/reference/androidx/exifinterface/media/ExifInterface]. The sidecar exists
because video and audio have no equivalent tag set and because EXIF is stripped by many sharing paths.

### Sidecar JSON schema (one per media file)

```json
{
  "schema": "fieldcapture.media.sidecar/1",
  "media_id": "5e1c…",
  "type": "PHOTO",
  "path": "media/2026_YT/Bradford_North/26YT-0042/lodging/20260614T150405Z_01.jpg",
  "sha256": "…",
  "bytes": 2841233,
  "timestamp": "2026-06-14T15:04:05.123Z",
  "timestamp_local": "2026-06-14T10:04:05.123-05:00",
  "trial": "2026_YT",
  "field": "Bradford North",
  "plot_id": "26YT-0042",
  "note_type": "lodging",
  "session_id": "walk-…",
  "position": { "lat": 38.9061234, "lon": -92.2691234, "accuracy_m": 2.1, "bearing_deg": 14.0, "source": "fused" },
  "assignment": { "method": "POLYGON", "distance_m": 0.8, "runner_up_distance_m": 2.9, "manually_corrected": false },
  "transcript": "lodging three",
  "person": "PT",
  "device": { "model": "Pixel 8a", "app_version": "0.1.0" }

```

Video sidecars add `"video": { "started_at": "…", "duration_ms": 1832000, "track": "tracks/walk-….gpx" }`.
Audio sidecars add `"audio": { "sample_rate_hz": 16000, "stt_engine": "vosk", "stt_confidence": 0.87 }`.

## Track sidecar written during recording

`sessions/<session_id>/track.ndjson`, one JSON object per line, appended as fixes arrive so an app kill
loses at most one line: `{"t":"2026-06-14T15:04:05.123Z","lat":38.9061234,"lon":-92.2691234,"acc":2.1,"alt":231.0,"spd":1.3,"brg":14.0,"src":"fused"}`.
The GPX in the export is generated from this file (or the `track_points` table) at export time.

## Field Book Table and Database exports

Field Book's Table format has one row per entry and one column per trait, without person/timestamp;
its Database format has one row per observation with person and timestamp [web:
https://docs.fieldbook.phenoapps.org/en/latest/export.html]. The exact column headers of Field Book's
own export files were not fetched, so this app writes its own two layouts under those names and labels
them "Field Book–style": `fieldbook_table.csv` = `plot_id` + import attributes + one column per trait;
`fieldbook_database.csv` = `plot_id, trait, value, timestamp, person, lat, lon` [inference]. A user who
needs a byte-identical Field Book export should import `plots.csv` into Field Book and export from there.

## Weather

`weather_daily.csv`: `field_id, date, source, tmax_c, tmin_c, precip_mm, et0_mm, srad_mj_m2, vp_kpa,
soil_moisture_0_7cm, fetched_at, request_url`. Sources: `OPEN_METEO_ARCHIVE`
(`https://archive-api.open-meteo.com/v1/archive`, ERA5/ERA5-Land, 5-day delay, daily variables including
ET0 and shortwave radiation) [web: https://open-meteo.com/en/docs/historical-weather-api],
`OPEN_METEO_FORECAST` (`https://api.open-meteo.com/v1/forecast`, includes soil temperature and
moisture layers) [web: https://open-meteo.com/en/docs], `DAYMET`
(`https://daymet.ornl.gov/single-pixel/api/data?lat=…&lon=…&vars=…&start=…&end=…`; tmax, tmin, prcp,
srad, vp, swe, dayl; 1 km; 1980 to the latest complete calendar year; no key) [web:
https://daymet.ornl.gov/web_services]. Every response body is kept as
`weather/<source>_<field_id>_<start>_<end>.json` next to the CSV.

## Soil

`soil.csv`: `field_id, plot_id, mukey, cokey, musym, muname, compname, comppct_r, majcompflag,
taxclname, fetched_at, query`. Source: Soil Data Access `POST https://SDMDataAccess.sc.egov.usda.gov/Tabular/post.rest`
with `QUERY` and `FORMAT=JSON+COLUMNNAME`, no key, 100,000-row cap [web:
https://sdmdataaccess.nrcs.usda.gov/WebServiceHelp.aspx]. The map-unit key for a point comes from
`SDA_Get_Mukey_from_intersection_with_WktWgs84('POINT(lon lat)')` [web:
https://sdmdataaccess.sc.egov.usda.gov/documents/AdvancedQueries.html]; components are then read from
`component` (`cokey, compname, comppct_r, majcompflag, taxclname`) joined to `mapunit` (`musym, muname`)
[web: https://ncss-tech.github.io/AQP/soilDB/SDA-tutorial.html]. The full query text is stored in `query`.

## Harvest import

Plot-combine software exports CSV. HarvestMaster Mirus exports comma-delimited files with plot
identifiers, weight, moisture, test weight, yield and plot size, in "Standard" or "Advanced" column
sets [web: https://harvestmaster.com/data/support/manuals/Mirus-for-GrainGage-HTML/6-Field_Maps.html];
the ARM integration guide confirms `.csv`/`.mtoa` output but not the header names [web:
https://gdmdata.com/media/documents/Connecting_ARM_with_HarvestMaster_Mirus.pdf?v=1606173431]. Because a
fixed header list is not publicly documented, import is mapping-based: the user maps file columns to
`plot_id, harvested_at, weight_kg, moisture_pct, test_weight, yield, yield_unit, plot_area_m2` once and
saves the mapping as a named profile (JSON in `field_import/harvest_profiles/`). `harvest.csv` export has
those columns plus `source_file, mapping_profile, imported_at`.

## GIS layers

Import: GeoJSON (RFC 7946) and KML (Placemark Point/LineString/Polygon only). Stored under `layers/`
unchanged; rendered as MapLibre GeoJSON sources. Not joined to plots; purely visual context (field
boundaries, tile lines, soil map unit polygons from `SDA_Get_MupolygonWktWgs84_from_Mukey`).

## Crossing

`crosses.csv`: Intercross columns first — `crossID, femaleObsUnitID, maleObsUnitID, timestamp, person,
experiment, type` [web: https://raw.githubusercontent.com/PhenoApps/Intercross/master/docs/export.md] —
then `lat, lon, accuracy_m, pollinations, pods_set, seed_count, notes, audio_path, session_id`.
Imports: Intercross parents (`id,name,sex`) and wishlist (`femaleDbId,maleDbId,femaleName,maleName,
wishType,wishMin,wishMax`) [web: https://raw.githubusercontent.com/PhenoApps/Intercross/master/docs/parents.md,
https://raw.githubusercontent.com/PhenoApps/Intercross/master/docs/crosses.md]. Whether Intercross reads a
file with extra trailing columns was not verified; the export dialog therefore offers an
"Intercross columns only" switch.

## Downstream schema (Shiny / Power BI)

One export folder is one star schema: `plots` (dimension, grain = plot) joined by `plot_id` to the
facts `planter_events`, `annotations`, `observations`, `media`, `harvest`, `samples`, `crosses`
(female/male), and by `field_id` to `weather_daily` and `soil`; `sessions` is a second dimension keyed
by `session_id`. `fieldcapture.sqlite` contains the same tables, so R (`DBI`/`RSQLite`) and Power BI
(SQLite ODBC or the CSV folder connector) read one source. Column names are lower snake case with unit
suffixes so no renaming is needed in the BI layer.
